# Keep reviewed narration; silence explicit sample ranges

This opt-in path addresses spoken-sensitive-information editing without deleting the entire lesson's narration. It uses the **same source SHA-256** for the video-mask and audio-mute plans. It creates a combined masked video with selectively muted audio, a separately listenable normalized WAV, and the original audio-free rendered copy as a fallback. It does **not** detect speech, names or secrets automatically.

The ordinary `render`, `verify`, `audit-masks` and `frame` commands retain their previous all-audio-removal behavior and bundle format. Do not use an audio-preserving output if you cannot review all of its remaining sound.

## Run an original synthetic example

```sh
python -m examples.selective_audio audio-demo
python -m frame_veil audio-inspect audio-demo/synthetic.mp4
python -m frame_veil audio-render audio-demo/synthetic.mp4 audio-demo/plan.json audio-demo/audio-plan.json --out selective-review
python -m frame_veil audio-verify selective-review
```

The original red-video/tone fixture has ten video frames and an 8 kHz mono AAC track. The plan silences overlapping decoded-sample intervals 2,000–4,000 and 3,000–5,000 (exclusive ends), preserving normalized PCM samples outside their union. Open `selective-review/review.mkv` in a trusted local player and listen to `selective-review/redacted.wav`. No browser playback support is promised. The example modules run from the checkout, not as installed commands.

## Supported inputs and coordinate system

All original video/container/hash limits apply. Additional requirements:

- Exactly **one audio track**, AAC or 16-bit PCM. Multiple tracks are rejected instead of silently retaining a different language/commentary track.
- Mono or stereo, sample rate 8,000 / 16,000 / 22,050 / 24,000 / 32,000 / 44,100 / 48,000 Hz.
- Video and audio stream start times are zero. Audio must have a sample-based time base and decoded frame timestamps contiguous from zero. Offsets, gaps or overlap are rejected, not silently collapsed into a different timeline.
- At most 64 MiB of normalized signed 16-bit PCM. Each existing media subprocess has a 120-second deadline. The supported format/size limits are not a decoder or memory sandbox.

`audio-inspect` actually decodes/counts the source audio and reports its hash, sample rate, channels and sample-frame count. AAC padding can make that count slightly longer than the nominal video duration. **Use the returned count, not a guessed duration multiplied by rate.** No `-shortest` trimming is applied; unmarked tail samples remain and require review. The complete output can therefore be slightly longer than its video.

A sample frame contains both channel samples together. `start_sample` is zero-based and `end_sample` exclusive. Both channels are set to signed PCM zero within each range. For a reviewed zero-start recording, seconds × sample rate can help identify a candidate boundary, but it is not a substitute for listening and adding adequate safety margin. The plan uses decoded samples, not compressed AAC packets or video-frame indices. Source/player clock behavior, word boundaries and the semantic correctness of your chosen intervals remain human responsibilities.

```json
{
  "schema": 1,
  "source_sha256": "EXACT_HASH_FROM_AUDIO_INSPECT",
  "sample_rate": 8000,
  "channels": 1,
  "samples": 16384,
  "mute_ranges": [
    {"start_sample": 2000, "end_sample": 5000}
  ]
}
```

Replace every inspected value from **your** source. Supply 1..100 explicit ranges. Empty, reversed, out-of-bounds, floating or boolean indices are rejected. Overlap is allowed. The video plan still uses the original frame-mask schema and must match the same source. A mismatched source/plan is rejected before an output bundle is published.

## Output and verification

The new output directory contains:

- `review.mkv`: FFV1 masked video plus one PCM-s16le audio track; no other streams or copied source metadata/chapters.
- `redacted.wav`: canonical two-channel-or-mono 16-bit PCM WAV used for the combined recording. Extra WAV chunks or trailing data are rejected by verification.
- `audio-plan.json`: the supplied, source-bound mute plan.
- `receipt.json`: hashes and bounded decoded-audio parameters.
- `video/`: the standard three-file audio-free video bundle, retained as a conservative fallback.

The source recording and unmuted normalized audio are not included. **Unmarked speech intentionally remains in the WAV and combined video**, so this bundle is not safe to share until the entire output has been reviewed. Rectangles, hashes and sample indices are not publication permission or consent from recorded participants. Technical container/encoder metadata can be generated by FFmpeg; this is not forensic metadata erasure.

Rendering normalizes the source to signed 16-bit PCM, copies those samples, and replaces only selected ranges with zero. It verifies that the final combined recording decodes to the exact reviewed WAV sample sequence. This preserves **normalized PCM** outside the ranges, not original compressed AAC bytes or arbitrary higher-precision source samples.

`audio-verify` reads a bounded private snapshot of the bundle and performs all of these checks:

1. Standard nested video hashes/stream/frame properties and source-plan bindings.
2. Audio plan, WAV and combined recording hashes, exact expected layout and decoded audio properties.
3. The combined recording's decoded PCM equals the supplied canonical WAV.
4. Every declared mute sample frame is zero in every channel.
5. The **actual combined recording's video**, not just the audio-free fallback, passes the independent per-frame opaque-mask audit.

A positive result establishes only consistency and the declared decoded zero samples/black rectangles. It does not authenticate the source, prove no one changed unmarked samples/pixels, certify timestamps or word-boundary choices, or detect unmarked privacy. An attacker can reconstruct internally consistent files; these are not signed proofs. A real test deliberately changes an unmarked sample, updates hashes and confirms this narrow audit still passes, demonstrating the limit.

Exit 0 indicates successful completion. Exit 3 with `declared_mutes_silent: false` reports the first mute range/sample failure, or reports a first video-mask failure through the existing mask-audit result; the audit did not complete. Exit 2 means input/structure/decode/timeout/filesystem failure. Never treat an incomplete or failed audit as privacy approval.

Output directories must be new. Files are prepared/validated privately before copying; a filesystem failure during final copy may leave an incomplete directory, which must not be used as a successful bundle. Original inputs are never overwritten. The temporary raw audio is cleaned up using the operating system's temporary-file lifecycle, not secure disk erasure. No network, transcription model, external upload or actual private recording is involved in the public tests.

## Verification and remaining classroom workflow gaps

53 public tests passed locally on Linux/Python 3.12.14 with FFmpeg 7.1.5, zero skips. Twenty added tests cover actual 8 kHz mono and 48 kHz stereo AAC rendering, **every** normalized source sample outside/inside the union of mute intervals, first/last sample boundaries, final WAV-versus-combined equality, rehashed nonzero muted samples, actual combined-video tampering, source metadata removal, absent/multiple/offset audio, timestamp-gap rejection, typed plan limits, extra WAV data, wrong source and CLI behavior. Existing all-audio-removal and pixel-audit tests still pass.

The gap/discontinuous-timestamp test isolates FFprobe output with a synthetic response; it is not a real corrupted-recorder corpus. No real lecture/voice recording, speech-detector accuracy, arbitrary codec corpus, Windows/macOS or browser playback was validated. Original topic #12 still lacks automatic visual/speech-sensitive-content detection, a segment-by-segment review interface and recorded human sign-off. This is a manually planned media-processing core, not the complete classroom privacy workbench.
